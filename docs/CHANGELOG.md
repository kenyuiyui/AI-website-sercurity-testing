## 2026-09 第十一輪：檢討「為了少誤報而漏掉東西」

起因：使用者問「這樣會不會為了減少誤報，犧牲了正確性與有效資訊？」。實際量測後，三個地方確實犧牲得太多，本輪補回來。

- **量測**：拿掉 XSS 的欄位白名單，該課表工具會從 11 筆變 63 筆；逐筆看那 52 筆，絕大多數是 GPA、學分數、星期名稱、class 名稱這類算出來的值，**但其中有一類是真的漏判**：先把資料組成字串變數、再把變數塞進 HTML（先 `const t = list.map(x => \`${x.name}\`)…`，再 `banner.innerHTML = \`…${t}…\``；出現在舊版資料夾，新版同一段已經加上跳脫）。
- **補上一跳變數追蹤**：插進 HTML 的是個變數時，回頭找同一個檔案裡 `const/let/var 該變數 =` 的那一段，用同一套規則判斷。只追一層——再多轉一手（函式回傳、跨檔案）仍然追不到，這條界線寫在模組註解裡。該專案因此多抓到 1 筆真的漏判。
- **後端訊號放寬**：原本只認 `fetch('https://…')` 與 `/api/` 路徑，`fetch('/users/' + id)` 這種打自家後端的最常見寫法會被漏掉，導致真正的越權問題被降級。現在任何「路徑字串」或樣板網址的 fetch、以及 `$.get`／`$.post`／`$.ajax` 都算有後端；Service Worker 的 `fetch(event.request)`（快取轉送，不是呼叫後端）仍然不算。誤判方向刻意偏向「算有後端」，因為那只是維持原本的行為，而漏判會把真問題藏起來。
- **降級不能變成假的安心**：結論會統計「被降級的項目裡原本屬於需要處理的有幾項」，並直說「如果那些檔案其實還在線上，請一併處理」。工具無法知道舊版本資料夾有沒有被發布，所以不能只用一句「需要處理 0」帶過。
- **仍然存在的界線（誠實記錄）**：XSS 只看欄位名稱像人打的文字、只追一層變數；`no-backend` 與 `old-version` 是情境推測，不是事實查核。驗證資料集裡沒有任何 XSS 案例，所以新規則的準確率目前只有實測專案的人工核對，沒有統計數字。

- **舊版本資料夾降級**：同一個 repo 出現兩個以上版本資料夾（`v1.0.0`、`v3.2` 這類命名）時，比較版本號找出最新的，其餘資料夾裡的發現降為「參考」並說明「舊版放著一樣會被打開，不再需要就整個刪掉或轉址到最新版」。金鑰類不降級（公開的舊版一樣會外洩）。
- **「參考」摘要寫出原因**：原本只有「都在測試／範例檔，或是假金鑰」一句；現在依實際情境列出（舊版本資料夾、這個專案沒有後端、沒在使用的檔案…）。
- **驗證**：該課表工具 66 檔 → 需要處理 0、請你確認 1（現役版本的 CSP 放寬）、參考 23（舊版 17、沒有後端 6）。作者打開只會看到一件該做的事。單檔式網站抓到 4 筆未跳脫（含 `textEl.innerHTML = text` 的提示訊息）；本專案自己維持需要處理 0、請你確認 0。新增 16 項回歸檢查。

## 2026-09 第九輪：兩個「答非所問」的來源

起因：拿 一個純前端的課表規劃工具（沒有後端，資料存在瀏覽器）實測，工具給出 10 筆「登入的人可能看得到或改得到別人的資料」。那個專案沒有登入、沒有伺服器、資料只存在使用者自己的瀏覽器，10 筆全是噪音。同時它現役版本的 CSP 寫著 `script-src 'self' 'unsafe-inline'`，頁面又有 99 個 `onclick=`，等於 CSP 幾乎擋不住 XSS——但我們只檢查「有沒有 CSP」，所以一個字都沒提，給了假的安心。

- **IDOR 要先看有沒有後端**：`scan-orchestrator` 新增 `projectHasBackend()`，比對伺服器框架（express／koa／fastify／flask／django／fastapi）、資料庫與 BaaS 客戶端（prisma／knex／mongoose／Supabase／Firebase）、對外 API 呼叫（`fetch('https://…')`、`/api/` 路徑、axios、XMLHttpRequest）、以及 `api/`、`server/`、`.py` 這類路徑。找不到任何跡象時，`possible_idor` 降為「參考」並附上原因（context `no-backend`）。判斷刻意寬鬆：只要有一點像後端就算有，寧可照常報，也不要把真的越權問題藏起來。訊號只看程式碼與字串、不看註解，所以「之後可能改用 axios」這種註解不算。
- **CSP 要看內容**（新 kind `csp_weak`）：有 CSP 但 `script-src`（或退而求其次的 `default-src`）含有 `'unsafe-inline'`、`'unsafe-eval'` 或 `*` 萬用字元時，報「請你確認」並說明「這些設定會讓 CSP 擋不住最常見的 XSS」。`style-src` 的 `unsafe-inline` 風險低很多，不報。取值用反向參照鎖定同一種引號，因為 CSP 內容本身就含單引號。
- **驗證**：該課表工具 66 檔 → 需要處理 2（兩個舊版本目錄沒有 CSP）、請你確認 1（現役版本的 CSP 放寬）、參考 10（越權，已註明專案沒有後端）；單檔式網站也正確抓出 CSP 的 `unsafe-inline`；Vue + Supabase 專案判定為「有後端」，行為不變。新增 10 項回歸檢查。

## 2026-09 第八輪：一個 repo 放好幾版網站時，主要入口挑錯

起因：拿 一個社群分享的專案當範例測試。那個 repo 用三個版本資料夾各放一份完整網站，沒有最上層的 index.html。原本的規則「深度最淺的 index.html 就是主要入口」在平手時取第一個，結果把最舊的版本資料夾講成主要入口，最新的版本反而被標成「另一個網頁」——對作者來說這是明顯的誤導。

- **主要入口只認最上層（根目錄）的 index.html**。沒有的話就視為「好幾份平行的網站」，每個網頁都是各自獨立的入口，不硬選一個，也不再出現「另一個網頁」這個容易誤會的標籤。
- **每個入口用自己的資料夾當根目錄**解析絕對路徑，所以版本資料夾裡的 `/js/app.js` 會正確對到該資料夾底下的檔案（原本會對到別的版本或對不到）。
- 驗證：該課表工具 66 檔 → 使用中 62、疑似沒用到 4（有兩組功能的程式檔在現役版本的 index.html 裡完全沒被載入，手動核對屬實）。新增 2 項回歸檢查。

## 2026-09 第七輪：「無法判斷」太多、看不到引用關係

起因：使用者看掃描本專案自己的檔案樹，10 個檔案標成「無法判斷」，並問「到底為何無法判斷」以及「入口檔會用到哪些檔案，能不能有關係圖」。查出來是自己踩到的雷：`modules/project-map.js` 的註解裡寫了「只用 regex 追 import(acorn 解析不了 TypeScript)」，`import(` 這幾個字被動態載入的規則命中，整個專案因此變成「無法確定」，所有追不到的檔案都只能標「無法判斷」。

- **引用追蹤只看真正的程式碼**：`project-map` 改用 `source-mask`。判斷引用時保留字串（引用路徑本身就是字串）、只抹掉註解；判斷有沒有動態載入時連字串一起抹掉（動態載入是語法，不會寫在字串裡），所以註解或測試資料裡提到 `import.meta.glob` 不再影響判斷。三個實測專案的「無法判斷」都歸零。
- **多追三種引用方式**：`require('./x')`（Node 工具鏈）、`<a href>`（頁面之間的連結）、以及能對上專案內某個檔案的字串路徑（`navigator.serviceWorker.register('/sw.js')`、`new Worker('./w.js')`）。
- **所有網頁都是入口**：`.html` 檔放上線後每一頁都打得開，不能只從 index.html 追。沒有被首頁連到的網頁改標成「另一個網頁」，不再和真正沒用到的檔案混在一起。
- **工具與測試鏈**：建置腳本與測試檔當第二批起點，它們 require 到的檔案標成「工具／設定」或「測試／範例」，不會被當成可以刪。工具目錄再加上 `eval/`、`benchmark/`；「建置／設定」改稱「工具／設定」。
- **畫面補上兩件事**：每種狀態的一句話說明（使用中＝從首頁一路引用得到、另一個網頁＝首頁沒連到但網址打得開……）；以及「網頁用到哪些檔案（引用關係）」的樹狀圖，從主要入口往下展開，共用的檔案第二次出現時標「同上」，最深 8 層。無法判斷時的原因也直接顯示在檔案樹旁邊，不用再去別的區塊找。
- **看得懂的顏色**（使用者回饋：凡是要給人看的都要做醒目的工作）：引用關係改成分層色塊，由外往內一層一個顏色（淺綠→淺黃→淺藍→淺紫→淺粉→灰，第 7 層起循環），層與層用內縮色塊表現包含關係；檔案樹的狀態從純文字 `[使用中]` 改成有顏色的標籤（使用中綠、疑似沒用到琥珀、另一個網頁藍、工具與測試灰），有待處理項目的檔案再加一個琥珀色圓標。顏色一律走 `:root` 變數（新增 `--lvl0`～`--lvl5`），深淺兩主題各一組。
- **驗證**：本專案自己 38 檔 → 使用中 19、另一個網頁 2、工具／設定 11、測試／範例 6，無法判斷 0；該 Vue 專案 104 檔 → 疑似沒用到 14（一個暫存網頁改歸「另一個網頁」）；單檔式網站 3 檔 → `sw.js` 靠字串路徑認出有在使用。新增 10 項回歸檢查。

## 2026-09 第六輪：單檔式網站整份被略過、結果畫面太雜

起因：使用者拿兩個專案回測。一是本專案自己，結果顯示 18 項，使用者以為是新的 bug（實際上 18 項全是「參考」，都在 `eval/`、`scripts/` 的測試檔，需要處理與請你確認都是 0）；二是 一個所有程式碼都寫在 `index.html` 的單檔式語音轉文字網站，結果只檢查到 2 個檔案、回報「沒問題」。

- **檔案大小上限 300KB → 2MB**：那個單檔式網站的 `index.html` 有 307KB，剛好超過上限被整份略過，等於網站的程式碼一行都沒看，報告卻說沒問題。實測 435KB 的檔案掃描只花 135ms，300KB 訂得太保守。
- **入口檔沒被檢查時要明說**：`project-map` 會比對被略過的清單，若其中有 `index.html`，結論改成「這次沒有檢查到你的網站主檔，結果不能當作『沒問題』」，並附上「把它直接拖進來」的做法，取代原本含糊的「找不到網站入口」。單檔式網站（入口沒有引用其他程式檔）的說明也改成正面描述，不再像是出了錯。
- **單檔式網頁的兩類誤報**：
  - SQL 規則的模板字面值／f-string 模式原本只要出現一個 SQL 關鍵字就報，`` `onblur="Card.update(${id})"` `` 這種組 HTML 的寫法、壓縮過的函式庫（含 `delete` 運算子）都會誤判。改成與字串拼接模式一致，必須同時出現第二關鍵字（FROM／INTO／WHERE／SET／VALUES）。

- **結果畫面改版**（使用者回饋：字太小、看起來雜亂）：
  - 「參考」整組預設收合成一行摘要（例如「參考 18 項：都在測試／範例檔，或是假金鑰，可以略過」），不再攤開成一長串卡片。跳轉到收合區塊裡的卡片時會自動展開。
  - 問題標題放大到 16.5px，並把「要做什麼」提到標題正下方、加底色獨立成一行，不必展開就看得到。
  - 說明從整段文字改成條列（以句號斷句）。8 種原本只有一長句的說明改寫成 2～3 句短句，報告同步受益。

### M6 idor-detector.js

- **允許 TS 回傳型別標註 `): Order {`,否則正則版整條漏判。**

  修正紀錄(2026,真實AI產出程式碼實測發現的漏判):
  原本 \)\s*{ 要求右括號後緊接大括號,但TypeScript常見的函式回傳型別標註
  (例如 function getOrder(id: number): Order { ... })在右括號跟大括號中間
  插入了 ": Order" 這段文字,導致整個正則完全匹配失敗、直接漏判。這不只
  影響AST版失敗後的降級情境——任何貼上帶回傳型別標註的TS函式,連正則保底版
  都抓不到。加上 (?:\s*:\s*[\w.<>\[\]| ]+)? 這段選擇性分組,允許右括號後、
  大括號前存在型別標註,但不解析型別內容本身(只是跳過,不影響其他判斷)。

- **參數名除 id/userId/req 外也認駝峰 xxxId(大寫 Id,避開 valid/grid)。**

  修正紀錄2(2026,真實Lovable專案[filla-app]實測發現的嚴重漏判):
  原本只認完全等於 id/userId/req 這三個精確名稱,但真實程式碼裡最常見的
  參數命名其實是 xxxId 駝峰形式(如 propertyId、taskId、orderId、assetId)——
  這在真實案例中比裸 id 更常見。原本的 \b(id|userId|req)\b 是單字邊界完全
  匹配,propertyId 裡的 "Id" 前面緊接 property(字母),不構成獨立單字邊界,
  完全匹配不到,導致這類函式全部被漏判。加上 [a-zA-Z_$][a-zA-Z0-9_$]*Id 這
  個分支涵蓋駝峰 xxxId 命名,要求 Id 是大寫開頭(符合JS駝峰慣例),避免誤傷
  valid/avoid/grid/solid 這類字尾剛好是小寫id、但語意無關的單字。

- **Express/Koa 路由 callback 寫法;主體用大括號配對取出,不能用 [^}] 截斷。**

  修正紀錄(2026,reference_cases/incident-moltbook-2026、incident-base44-2025 發現):
  IDOR_PATTERN 只認具名 function 宣告,Express/Koa 路由最常見的「callback 直接當參數」
  寫法 app.get(path, async (req, res) => {...}) 與 app.get(path, function (req, res) {...})
  完全抓不到(AST 版沒有這個問題,只影響 acorn 無法載入時的保底路徑)。
  這條規則只比對 callback 的開頭,不要求參數名是 id/xxxId——路由 callback 的簽名固定是
  (req, res),實際查詢用的 ID 在 req.params 裡。也順帶涵蓋指派給變數的箭頭函式
  (const deleteOrder = async (req, res) => {...})。
  函式主體改用大括號配對取出(extractBraceBody),不沿用 IDOR_PATTERN 的 [^}]{0,300}:
  路由 callback 幾乎一定含 { appId } 解構或 findOne({...}) 這類物件字面值,
  [^}] 會在第一個 } 就截斷主體,導致後面的 DB 呼叫看不到而漏判。

- **必須是「擁有權比較」才算已檢查;只檢查有沒有登入(session)不算。**

  修正紀錄(來自真實案例實測發現的問題):原本的 isAuthRelatedNode 只判斷
  「有沒有出現」owner/session/auth 等權限相關字樣,但這樣會把「只檢查有沒有登入」
  (例如 if(!req.session.userId){...},只確認使用者存在,不比較資料擁有者)
  誤判為「已做擁有權檢查」而放過,這正是 IDOR 漏洞最典型也最危險的樣式——
  有登入檢查、卻沒有擁有權檢查。

- **Acorn 原生不認 JSX,需 acorn-jsx 外掛,否則 React 程式碼一律退回正則版。**

  修正紀錄(2026,真實AI產出程式碼實測發現的問題):
  Acorn 是純 JavaScript parser,原生完全不認識 JSX(<div>...</div> 這類語法)。
  實測發現:貼上任何一段含 JSX 的 React 元件(.tsx/.jsx,這正是 Lovable/v0/Bolt

  從100%(AST版)掉回77.8%(正則版),且這個降級對使用者完全不可見。

- **回傳 astUsed,讓畫面提示「這次 IDOR 用的是較弱的正則版」。**

  修正紀錄(2026,真實AI產出程式碼實測發現的問題):
  idorDetector(code) 原本在AST解析失敗時靜默退回正則版,呼叫端完全無法得知

  (不是例外狀況),不應該讓使用者在完全不知情下拿到涵蓋率較低的結果。

  Line Bot Access Token 原本跟 OpenAI/Anthropic/AWS 等金鑰混在同一份 KEY_RULES 裡,
  套用同一個 tier1「明文金鑰外洩」等級。這是不準確的——LINE 官方文件說明
  channel access token 是「不透明字串(opaque string)」,沒有公開的固定格式規則
  (不像 sk-proj-/AKIA 等有明確字首),原本的正則 /[A-Za-z0-9+/=]{100,}/ 只是「任意
  100字元以上的base64字元集合字串」,會誤判任何長JWT、base64編碼圖片、簽章值等
  完全不相關的內容。實測發現:貼上一組 Supabase JWT 金鑰,會被同時誤標成
  「Line Bot Access Token 外洩」(因為JWT本身也是100+字元的base64字元集合)。
  因此 Line Bot 比照 Firebase 的處理方式從 KEY_RULES 抽出,獨立成
  lineBotTokenDetector:(1) 明確排除三段式JWT格式(xxx.yyy.zzz,已由M2 JWT分析器
  專責處理,不應由這條規則重複標記或誤標成別的廠商),(2) 降為 tier2「建議複查」
  而非 tier1「高信心度發現」,文案上誠實反映「這條規則沒有可靠格式特徵可比對,
  誤判率高於其他已知格式金鑰」,避免使用者把這類低可靠度的比對結果當成確診。

- **排除 JWT 片段要檢查「前後緊鄰」是否有 .xxx 段,只看匹配片段本身會失效。**

  修正紀錄(2026,真實Lovable專案實測發現的問題):
  原本只用 JWT_SHAPE_PATTERN.test(matched) 檢查「匹配到的片段本身」是否為
  完整三段式JWT,但這個排除邏輯幾乎永遠失效——因為JWT的分隔符號 "." 不在
  LINE_BOT_TOKEN_RULE.re 的字元集合[A-Za-z0-9+/=]內,正則掃描遇到"."就會
  截斷,實際只抓到JWT三段中的其中一段(通常是payload),這段本身當然不符合
  "xxx.yyy.zzz"的完整格式,排除判斷因此形同虛設。實測發現:一組真實的
  Supabase anon JWT會同時被M1的supabase_anon規則正確標記,又被這裡誤標成
  Line Bot token,兩者互相矛盾,使用者會很困惑。
  修法:不檢查「匹配片段本身」,而是檢查「匹配片段的前後緊鄰處」是否存在
  JWT的其他兩段(用.分隔、同樣是base64-like字元的片段)——如果前面或後面
  緊接著 "." + 另一段長度合理的base64-like字元,代表這其實是嵌在一個更大
  JWT結構裡的其中一段,應該排除,交給M2(jwt-analyzer)處理整個JWT。

### M7 language-detector.js

- **Python import 規則必須排除 JS/TS 的 ES Module import,否則幾乎所有 TS 檔都誤判。**

  修正紀錄(2026,真實Lovable專案[filla-app]實測發現的嚴重誤判):
  原本 PYTHON_PATTERN 裡的 \bimport\s+\w+\b 這條子規則,目的是抓Python的
  裸import語句(如 import os),但寫法完全沒排除JavaScript/TypeScript的
  ES Module import語法。實測發現:任何一份標準的TS/JS檔案,只要有
  `import type { X } from "./y"`(TypeScript專屬語法)或
  `import React from "react"`(一般default import)這類再正常不過的寫法,
  都會被誤判成「含Python特徵」,對使用者顯示一段誤導性的警告文字,
  說這份程式碼的規則涵蓋範圍有限——而它明明就是規則主要針對的
  JavaScript/TypeScript語言本身。這是影響面極廣、幾乎必現的誤判
  (幾乎所有現代TS/JS檔案都有import語句),比其他已知限制嚴重得多。

### M9 sql-injection-detector.js

- **字串拼接用限長寬鬆匹配 [\s\S]{0,120}?,不能用引號邊界(SQL 內常含單引號)。**

  修正紀錄(來自真實案例實測發現的bug):
  初版 CONCAT_PATTERN 用「排除引號字元的字元類別」([^"'`]) 來界定字串邊界,
  目的是避免比對跨越多個不同字串。但這個做法有嚴重副作用: SQL 查詢字串
  內部經常自己就包含單引號(例如 "...username='" + username + "'..."),
  正則在字串開頭遇到內部的單引號就會提早截斷比對,導致真正的字串拼接
  反而被漏判。改用「限制比對長度的寬鬆匹配」([\s\S]{0,120}?)取代嚴格
  的引號邊界匹配,犧牲一點點精確度換取不漏判真實案例中最常見的寫法。
  (此問題是在拿真實世界案例實測時發現,原本的單元測試案例湊巧沒有
  觸發這個邊界,這正是「真實案例測試」相對於「手寫假案例測試」的價值所在)

- **SQL 關鍵字需搭配第二關鍵字(FROM/INTO/SET…)才算語句,避免一般文字誤判(fp-26)。**

  修正紀錄2(誤判率驗證發現的問題,見 eval/FALSE_POSITIVE_REPORT.md fp-26):
  修正1解決了漏判問題,但換來另一個副作用:CONCAT_PATTERN 只要求「SQL關鍵字
  附近有拼接」,沒有要求這真的是一句完整的SQL語句,導致一般文字說明裡剛好
  提到SQL關鍵字(例如 "Use SELECT statements carefully" + userNote 這種
  提示文字或註解),也會被誤判為疑似SQL Injection。
  修正:要求SQL關鍵字後方(60字元內)還要出現對應的第二關鍵字
  (SELECT/DELETE 對應 FROM,INSERT 對應 INTO,UPDATE 對應 SET,
  也接受 WHERE/VALUES 作為輔助判斷),兩者都出現才算是真正的SQL語句結構,
  而不只是「提到SQL關鍵字的普通文字」。用完整的既有測試集(true positive
  案例、eval/samples.js真實案例)驗證過,加上這個限制不會讓任何真實的
  SQL Injection案例漏判,只排除了「關鍵字單獨出現、不構成完整語句結構」
  的情況。
