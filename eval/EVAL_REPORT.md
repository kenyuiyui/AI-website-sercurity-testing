# 真實世界案例評測報告

## 目的

不是再驗證「工具邏輯有沒有照著規格跑」（這是 `test/*.test.js` 在做的事），而是驗證「拿真實世界會出現的 AI 產出程式碼樣式去測，工具實際抓得到多少」。這兩件事是不同層次的驗證——單元測試用的是為了驗證規則而寫的乾淨範例，真實案例會有更多干擾、更多邊界情況，容易暴露規則設計本身的盲點。

**這份評測直接改出了三個真正的 bug**，詳見下方「發現與修正」。

## 案例集設計原則

`eval/samples.js` 裡的 10 個案例，依據以下公開報告改寫成代表性範例（非逐字複製真實外洩程式碼）：

- Veracode 2026 GenAI Code Security Report（AI 生成程式碼平均安全通過率、各類漏洞占比）
- Georgia Tech Vibe Security Radar（AI 生成後端程式碼權限設定過寬的統計）
- Lovable IDOR 外洩事件的公開技術分析（案例 #2 依此改寫）

10 個案例涵蓋 9 種工具現有涵蓋的問題類型，加 1 個**刻意放入的涵蓋範圍外對照組**（AWS IAM policy JSON，工具完全不涵蓋雲端 IAM 設定檢查）——放這個對照組不是為了扣分，是為了誠實驗證「工具真的抓不到這類問題」而非遺漏測試，呼應報告裡「沒有查證過的判斷比沒有判斷更危險」的核心原則。

## 怎麼跑

```bash
cd pkg/eval

# 情境A: acorn 不可用(模擬CDN載入失敗/離線,也是預設保底狀態)
node run_eval.js

# 情境B: acorn 可用(模擬CDN成功載入,AST版完整分析)
node -e "global.acorn = require('../node_modules/acorn'); require('./run_eval.js');"
```

## 結果

| 情境 | 命中率 | 漏判 |
|---|---|---|
| acorn 不可用（正則保底版，CDN失敗/離線時的真實表現） | **7/9 = 77.8%** | 案例 #2、#3（皆為 IDOR） |
| acorn 可用（AST完整分析，CDN成功載入時的表現） | **9/9 = 100%** | 無 |

案例 #10（IAM policy）兩種情境下都正確地「沒有誤報任何東西」，符合預期——這代表工具在遇到自己不涵蓋的問題類型時，不會硬湊一個假結果出來，這件事跟「有沒有抓到問題」同等重要。

**這兩個數字都要老實看待，不能只講 100% 那個。** 使用者的瀏覽器不一定能連上 Acorn 的 CDN（企業網路限制、離線環境、CDN 本身故障），77.8% 才是工具「保底一定做得到」的水準，100% 是「條件允許時的最佳水準」。這正是當初設計「正則保底 + AST 疊加」架構的理由——但也代表**正則保底層本身的品質，直接決定了工具在最壞情況下值不值得信任**，這也是為什麼下方三個修正裡有兩個是動到正則層。

## 發現與修正

拿真實案例測試前，全部 8 個模組的單元測試（含手寫的 true positive/negative 案例）都是 100% 通過的。這份評測用了三個更貼近真實世界的案例，就直接測出三個單元測試沒抓到的 bug：

### Bug 1：SQL Injection 正則版漏判「字串內部自帶引號」的常見寫法

**案例 #4**：`"SELECT * FROM users WHERE username='" + username + "'..."` 這種寫法非常常見（SQL 語法本身就需要用單引號包住字串值），但原本的正則設計用「排除引號字元」的方式界定字串邊界，遇到 SQL 字串內部自己的單引號就提早截斷比對，導致這個最典型的危險寫法反而被漏判。

**修正**：改用「限制比對長度的寬鬆匹配」取代「嚴格引號邊界匹配」，犧牲一點點理論精確度換取不漏判真實世界最常見的樣式。詳見 `src/modules/sql-injection-detector.js` 內的修正紀錄註解。

### Bug 2：IDOR 正則版不支援 `export async function` 語法

**案例 #2、#3**：AI 生成的 Express/Next.js API route handler 很常見寫成 `export async function getOrder(req, res) {...}`，原本的正則只認 `function xxx(){}`，完全沒考慮 `export`/`async` 前綴，導致這種現代常見寫法整個漏判。

**修正**：正則加上選擇性的 `(?:export\s+(?:default\s+)?)?(?:async\s+)?` 前綴支援。

### Bug 3：AST 版把「只檢查有沒有登入」誤判為「已做擁有權檢查」（最關鍵的一個修正）

**案例 #2**：原本 AST 版的邏輯是「函式體內只要出現 `owner`/`session`/`auth` 等字樣就視為已檢查」。但 `if (!req.session.userId) { return 401; }` 這種寫法，**只確認了使用者有沒有登入，完全沒有比較「這筆資料是不是屬於這個使用者」**——這正是 IDOR 漏洞最典型、最危險的樣式（Lovable 事件就是這個模式），卻因為程式碼裡出現了 `session` 字樣而被誤判為安全。

**修正**：判斷邏輯改為「子樹中是否存在**比較運算**（`===`/`!==`/`==`/`!=`），且至少一邊牽涉權限/擁有者相關的識別字或屬性」，而不是「有沒有出現特定字樣」。真正的擁有權檢查一定牽涉「比較兩個值是否相等」（資料的擁有者 vs 目前使用者），單純的登入檢查只是「存不存在」的判斷，不涉及比較。詳見 `src/modules/idor-detector.js` 內 `isOwnershipComparisonNode` 的完整說明。

這是三個修正裡**風險最高**的一個——因為修改判斷邏輯核心，可能讓原本正確判定為安全的案例變成誤判。修正後跑了完整回歸測試（含原本測試套件裡「有做擁有權比較、應判定安全」的核心案例），確認沒有引入新的誤判，才定案。

## 這份評測告訴我們的事

1. **手寫的單元測試案例不能取代真實案例測試**——三個 bug 都是規則設計者容易忽略的真實世界變化型：SQL 語句自帶引號、現代 export 語法、以及「登入檢查」與「擁有權檢查」的語意混淆。
2. **正則保底層的品質很重要，不能因為有 AST 疊加就輕忽**——CDN 不一定每次都連得上，77.8% 是使用者實際會遇到的下限。
3. **這次評測是一次性的，不是自動化回歸的一部分**——`eval/` 資料夾跟 `test/` 資料夾的定位不同：`test/` 是每次改動都要跑的自動化驗證，`eval/` 是階段性拿真實案例做健康檢查用的，之後累積更多真實案例時可以再跑。

## 下一步可以做的事（尚未進行）

- 案例集目前只有 10 個，覆蓋 9 個現有涵蓋的類型各 1-2 個，樣本數偏少。可以持續累積更多真實世界變化型（例如不同框架的 IDOR 寫法、不同 ORM 的 SQL 拼接模式）擴充這個案例集，讓評測更有代表性。
- 目前的評測是「工具有沒有抓到預期的問題」，還沒系統性測試「工具會不會對安全的程式碼誤報」（false positive rate）。這需要另外準備一批「看起來像有問題但其實是安全寫法」的案例集，是值得做的下一步。
