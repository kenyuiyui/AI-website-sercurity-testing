# 準確度評測報告

這份檔案回答一個問題:**拿真實世界會出現的 AI 產出程式碼樣式去測,這個工具實際抓得到多少?**
跟 `eval/run_rule_regression.js`(驗證「規則有沒有照著規格跑」)不是同一件事——
回歸測試用的是為了驗證規則而寫的乾淨範例,真實案例有更多干擾與邊界情況,會暴露規則設計本身的盲點。

**所有數字都是跑出來的,不是手寫的。** `npm run verify` 有一關會實際重跑評測、比對本檔與 README 的數字,
對不上就紅燈(見 `scripts/check-eval-numbers.js`)。

## 兩套案例集

| 案例集 | 位置 | 內容 | 用途 |
|---|---|---|---|
| 主要 | `eval/cases/*.txt` | 49 個(應偵測 20 個／應安全放行 29 個),含公開學術資料集 SecurityEval 改寫的樣本 | README「準確度驗證」的數字來源;有統計信賴區間 |
| 早期 | `eval/samples.js` | 10 個(9 個應偵測 + 1 個刻意放的涵蓋範圍外對照組) | 專案初期的評測;同時是行為快照的輸入之一 |

`eval/reference_cases/` 是依公開事件或問題模式改寫的參考案例,**刻意不計入統計**(改寫會帶入預期偏誤),
只在回歸測試裡確認「該命中的有命中」。

## 這些數字要怎麼看

- **信賴區間比百分比誠實。** 命中率的樣本只有 20 個,區間寬到 ±11.4 個百分點;
  「95.0%」的真正意思是「大概在 76% 到 99% 之間」。`run_scaled_eval.js` 會自己印出還差幾個樣本才收斂到 ±5pt。
- **誤判率 0% 同理。** 29 個 true negative 撐起來的 0%,區間下界是 88.3%。丟 500 個真實檔案進來不會是 0%。
- **信賴區間成立的前提是案例來自真實蒐集。** 如果案例是為了驗證規則而發想出來的,帶著出題者的預期偏誤,
  區間的數學意義就失真了。這點腳本輸出的最後一段也會提醒。
- **網頁版一律走 AST 完整版**(acorn 放在本站 `vendor/`,不依賴外部 CDN)。
  正則保底版是「程式碼含 TypeScript 型別語法、語法分析解析不了」時的退路,
  它唯一的漏判是 `legacy-tp-002`:函式裡出現 `session` 字樣就當成已檢查權限,分辨不出那只是登入檢查。
  這是正則能力的天花板,不是可以補的 bug。

## 當初這份評測抓出來的三個 bug

專案初期,全部模組的規則測試都是 100% 通過的;拿三個貼近真實世界的案例一測,直接測出三個測試沒抓到的 bug。
這是這份檔案存在的原因,也是「手寫測試不能取代真實案例」最具體的證據。

### 1. SQL 拼接:字串內部自帶引號就漏判

`"SELECT * FROM users WHERE username='" + username + "'..."` 這種寫法非常常見(SQL 語法本身就要用單引號包住值),
但原本的正則用「排除引號字元」界定字串邊界,遇到 SQL 字串自己的單引號就提早截斷,
最典型的危險寫法反而被漏判。改成「限制比對長度的寬鬆匹配」,犧牲一點理論精確度換取不漏判。
見 `modules/sql-injection-detector.js`。

### 2. IDOR 正則版不認得 `export async function`

AI 生成的 API route handler 很常寫成 `export async function getOrder(req, res) {...}`,
原本的正則只認 `function xxx(){}`,完全沒考慮 `export`／`async` 前綴。
加上選擇性前綴 `(?:export\s+(?:default\s+)?)?(?:async\s+)?` 解決。見 `modules/idor-detector.js`。

### 3. 把「登入檢查」誤判成「擁有權檢查」(最關鍵的一個)

原本 AST 版的邏輯是「函式體內出現 `owner`／`session`／`auth` 字樣就視為已檢查」。
但 `if (!req.session.userId) { return 401; }` **只確認了有沒有登入,沒有比較這筆資料屬不屬於這個使用者**——
這正是越權存取最典型的樣式,卻因為出現了 `session` 字樣被判定為安全。

改成:子樹中必須存在**比較運算**(`===`／`!==`／`==`／`!=`),且至少一邊牽涉權限／擁有者相關的識別字或屬性。
真正的擁有權檢查一定牽涉「比較兩個值是否相等」,單純的登入檢查只是「存不存在」的判斷。
見 `modules/idor-detector.js` 的 `isOwnershipComparisonNode`。

這是三個修正裡風險最高的一個(動到判斷邏輯核心,可能讓原本正確判為安全的案例變成誤報),
所以修正後跑了完整回歸,確認沒有引入新的誤判才定案。

## 還沒做到的事

- **命中率的樣本數仍然偏少。** 20 個應偵測項目,信賴區間 ±11.4 個百分點;
  要收斂到 ±5pt 估計還需要約 62 個。累積不同框架的越權寫法、不同 ORM 的 SQL 拼接樣式是最直接的補法。
- **誤判率同理**,29 個 true negative 估計還差約 6 個才到 ±5pt。
- **沒有真人使用測試的資料。** 所有準確度數字都是自己出題自己改。
  「不懂程式的人看不看得懂結果」這件事,自動化測試證明不了,腳本在 `docs/USER_TEST_KIT.md`,結果要靠實際找人跑。

## 怎麼跑

```bash
npm run eval          # 早期案例集,正則保底版
npm run eval:ast      # 早期案例集,AST 完整版
npm run eval:fp       # 誤判率
node eval/run_scaled_eval.js   # 主要案例集 + 信賴區間
```

`eval/eval-orchestrator.js` 呼叫的是跟網頁同一支 `modules/scan-orchestrator.js`,所以評測結果就是上線行為。
新增案例:`eval/cases/*.txt`,格式見 `eval/CASE_FORMAT.md`。
