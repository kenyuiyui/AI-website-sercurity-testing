# 誤判率驗證報告（False Positive Evaluation）

## 目的

`eval/EVAL_REPORT.md` 驗證的是「工具有沒有抓到該抓的問題」（true positive 導向）。這份報告驗證相反方向：**工具會不會對正確、安全的程式碼誤報**（false positive）。兩份報告合起來才是完整的準確度圖像——只驗證其中一個方向，另一個方向可能藏著沒被發現的問題。

## 測試集設計

`eval/false_positive_samples.js`，**29 個案例**（第二輪擴充，原本17個），涵蓋 M1、M2、M3、M4、M5、M6、M9、M10 共 8 個模組（M7 語言偵測、M8 畫面呈現不涉及誤判判斷，不需要涵蓋）。每個案例都是**真的安全、正確使用防護措施的程式碼**，且刻意寫得「表面上容易觸發規則」——例如：

- 用環境變數讀取金鑰（正確做法），而不是寫一段完全不含任何金鑰特徵的無關程式碼
- 正確做了擁有權比較檢查的 IDOR 防護（含具名函式與箭頭函式兩種寫法，涵蓋正則版與 AST 版）
- 正確使用參數化查詢、ORM 方法
- MD5 用在檔案校驗這種合理場景（不是密碼儲存）

**第二輪新增兩類案例**（fp-18 ~ fp-29）：

1. **Python/Django/Flask 真實慣用寫法**（fp-18~fp-23）：依官方文件查證後撰寫，包括 Django `Model.objects.raw()` 搭配 `%s` 佔位符、`connection.cursor()` 參數化查詢、Flask `os.environ.get()`／`os.environ[...]` 兩種讀取金鑰的官方推薦寫法、`json.loads` 安全反序列化。第一輪的 17 個案例偏重 JavaScript，Python 只涵蓋 1 個模組，這輪補齊到涵蓋 M1/M4/M6/M9/M10 共 5 個模組的 Python 情境
2. **邊界值測試**（fp-24~fp-29）：第一輪完全沒有涵蓋「規則設計最容易出錯的地方」——長度剛好卡在門檻邊緣的字串、大小寫混合、關鍵字出現在非預期上下文（例如 SQL 關鍵字出現在普通說明文字裡）、命名不遵循常見慣例但邏輯正確的程式碼

這樣設計是為了讓測試真正檢驗規則的判斷邊界夠不夠精確，而不是找一堆「明顯不會觸發」的案例交差。

## 過程：發現並修正一個真實誤判（第一輪）

第一輪跑出來是 **1/17 誤判（5.9%）**，案例 fp-8：

```js
const dbPort = process.env.DB_PORT || "5432";
```

`M4 secret-heuristics` 的環境變數 fallback 規則把 `"5432"`（PostgreSQL 預設連接埠）標記成疑似密鑰。原因：`ENV_FALLBACK_PLACEHOLDER` 判斷式當時只排除了明顯的佔位字樣（`your-`、`placeholder` 等）跟 `localhost`，沒有排除純數字。但**密鑰不可能是純數字**——這是一個能安全排除、不會影響任何真實密鑰偵測的類別。

修正：`ENV_FALLBACK_PLACEHOLDER` 新增 `/^\d+$/.test(val.trim())` 排除規則。修正後跑了完整回歸測試（130個單元測試 + 這份 17 案例的誤判測試），確認沒有讓任何真正的密鑰漏判，才定案。

## 過程：發現並修正第二個真實誤判（第二輪，邊界值測試發現）

第二輪擴充到 29 案例後，跑出 **1/29 誤判（3.4%）**，案例 fp-26：

```js
const helpText = "Use SELECT statements carefully" + userNote;
```

`M9 sql-injection-detector` 的字串拼接規則，原本判斷邏輯是「SQL 關鍵字（SELECT/INSERT/UPDATE/DELETE）附近有拼接運算就標記」，沒有要求這真的構成一句完整的 SQL 語句。這句話只是提到 `SELECT` 這個字的一般說明文字，跟後面的 `userNote` 拼接，卻被誤判為疑似 SQL Injection。

**這個誤判是第一次修正（fp-4，解決字串內含引號漏判）留下的副作用**——當時為了不漏判「SQL 字串內部自帶引號」的常見寫法，把判斷條件放寬成「SQL 關鍵字附近有拼接即算數」，但沒有同步收緊「這是不是真的 SQL 語句」的判斷，兩次修正合起來才暴露出這個邊界問題。這正是為什麼誤判率驗證要用**專門設計的邊界值案例**，而不是只補充「明顯安全」的案例——邊界值往往才是規則設計真正的弱點所在。

修正：要求 SQL 關鍵字後方（60字元內）還要出現對應的第二關鍵字（`FROM`/`INTO`/`WHERE`/`SET`/`VALUES`），兩者都出現才判定為真正的 SQL 語句結構。用完整的既有測試集（包含之前發現的引號拼接案例、真實案例 #4、長欄位清單 SELECT、UPDATE SET 語句）驗證過，確認沒有讓任何真實案例漏判，才定案。修正後：真實案例命中率維持不變（正則版 77.8%、AST版 100%），誤判率從 3.4% 降到 0.0%。

## ⚠️ 誠實的樣本限制（這點很重要，不要只看到「0% 誤判率」這個數字）

**29 個案例仍然不足以代表「這個工具在真實世界裡的誤判率是 0%」。** 這份測試集的價值是：

1. **驗證了每個模組至少能正確放行一種「正確使用防護措施」的典型寫法**——這是最基本的把關，確認規則邊界不會粗暴到「只要出現關鍵字就誤報」
2. **抓到了兩個真實存在的誤判**（純數字 fallback、SQL 關鍵字誤入一般文字），證明這個測試方向持續有效，不是形式主義的過場測試
3. **兩輪修正呈現一個規律**：第一次修正解決漏判問題時，可能會意外放寬判斷條件、留下新的誤判空間；下一輪擴充測試集時如果針對性地補邊界案例，往往能抓到這類「修正引入的副作用」。這代表**誤判率驗證不是一次性的事，每次調整規則後都應該重新跑一次**
4. **不代表**涵蓋了所有可能觸發誤判的寫法變化——真實世界的程式碼寫法遠比 29 個案例豐富，尤其是：
   - 更多程式語言、更多框架的慣用寫法（目前 Python 已補強到 5 個模組，但 Ruby、Go、Java 等完全沒有涵蓋）
   - 更複雜、多層嵌套的程式碼結構
   - 更多邊界值組合（目前只測了 6 種邊界情況，規則裡可能還有其他沒被想到的邊界）
